# Authorization Service — Interview Prep

Based on your actual code in `services/authorization-service` (C++17, librdkafka, libpqxx, nlohmann/json) inside the payment platform described in `revised arch.pdf`. Questions are ordered by how likely an SDE interviewer is to ask them, from "walk me through your service" basics up to deep systems-design follow-ups. Use Top 10 as your elevator pitch, 11–25 as the "if they dig deeper" layer, and 26–50 as the "senior/staff follow-up" layer you should at least have an opinion on, even if it's "we didn't do this, and here's what I'd change."

## TOP 10 — Must-nail basics

### Q1: Walk me through the end-to-end flow of a message through your service — what does it consume, what does it do, what does it produce?
**Polished answer:** The service is a Kafka consumer-and-producer pair wrapped around a validation engine. On startup, `main.cpp` builds a `KafkaConsumer` subscribed to the `payment_initiated` topic (consumer group `authorization-service-group`). Every message it polls is immediately handed off to a `ThreadPool` via `enqueue_detach` — the consumer thread itself does no business logic, it just keeps polling. Each worker thread parses the JSON payload into a `PaymentInitiatedEvent`, calls `AuthorizationEngine::authorize()`, which runs one SQL query against PostgreSQL to validate the user, payment intent, payment method, card expiry, and account balance. Based on the boolean result, it builds a `PaymentAuthorizedEvent` with `status = "AUTHORIZED"` or `"FAILED"`, serializes it back to JSON, and publishes it to either `payment_authorized` or `payment_failed`. Anything that throws during processing gets routed to a `payment_initiated.DLT` (dead-letter topic) instead of being silently dropped.
**TL;DR:** Kafka consumer (`payment_initiated`) → thread pool → one DB query for validation → Kafka producer (`payment_authorized` / `payment_failed`, or `.DLT` on error).

### Q2: Why decouple the Kafka consumer thread from the actual processing work using a thread pool instead of processing synchronously in the poll loop?
**Polished answer:** `KafkaConsumer::start()` calls `consumer_->consume(1000)` in a tight loop. If that same thread also ran the DB query and JSON work, the consumer would only be able to process one message every however-many milliseconds the DB round trip takes, and — more importantly — it would fall behind on polling, risking consumer-group rebalances or `max.poll.interval` timeouts. By doing `tpool.enqueue_detach(...)` and immediately looping back to `consumer_->consume()`, the poll loop's only job is to keep pulling messages off the broker and off-loading them, so throughput scales with the size of the thread pool (default 100 threads) instead of being serialized behind one thread's DB latency. This is the standard "fast consumer loop + fan-out to workers" pattern.
**TL;DR:** Keeps the Kafka poll loop hot so it doesn't stall/rebalance; real work happens in parallel worker threads instead of serially on the consumer thread.

### Q3: Explain your authorization SQL query. Why one query instead of four separate lookups (user, intent, method, balance)?
**Polished answer:** `AuthorizationEngine::authorize()` runs a single query with three `LEFT JOIN`s off the `users` table — to `payment_intents` (matched on intent id + user id), `payment_methods` (matched on method id + user id), and `accounts` (matched on `account_type = 'USER_WALLET'`) — filtered by `WHERE u.id = $1`. That's one network round trip to Postgres per message instead of up to four, which matters a lot at the "10k RPS" throughput the code comments claim. Because it's a `LEFT JOIN`, a missing intent/method doesn't fail the whole query — it comes back as `NULL` in that row, and the code explicitly checks `is_null()` on each field to produce a specific rejection reason ("Payment intent not found or mismatch", "Payment method not found...", etc.) rather than a generic failure. The trade-off is the query does more work per call (extra joins) and a `NULL`-checking code path is slightly harder to read than four separate happy-path queries.
**TL;DR:** One round-trip query with LEFT JOINs instead of 3–4 sequential queries, trading a bit of query complexity for far lower per-message DB latency.

### Q4: How do you prevent SQL injection here?
**Polished answer:** The query uses positional placeholders (`$1::uuid`, `$2::uuid`, `$3::uuid`) and `tx.exec_params(query, event.user_id, event.payment_intent_id, event.payment_method_id)` — libpqxx's parameterized-execution API. That means the values are sent to Postgres separately from the SQL text as bind parameters; Postgres compiles the query once and binds the parameters at execution time, so there's no way for user-controlled string content to be interpreted as SQL syntax. This is the C++/libpqxx equivalent of a Java `PreparedStatement`.
**TL;DR:** Parameterized queries (`exec_params` with `$1/$2/$3` placeholders) — values are never string-concatenated into the SQL.

### Q5: Explain your `ConnectionPool` — how is it thread-safe, and how does it handle a dead connection?
**Polished answer:** `ConnectionPool` holds a `std::vector<std::shared_ptr<pqxx::connection>>` guarded by a `std::mutex` and a `std::condition_variable`. `get_connection()` takes the lock, and calls `condition_.wait(lock, [this]{ return !pool_.empty(); })` — so if every connection is checked out, the calling worker thread blocks (doesn't spin) until one is returned. It pops one connection, unlocks, then checks `conn->is_open()`; if the connection died (e.g., Postgres restarted, network blip), it transparently creates a fresh `pqxx::connection` instead of handing back a broken one. `return_connection()` locks, pushes the connection back, and calls `condition_.notify_one()` to wake exactly one waiter. On the calling side, `AuthorizationEngine.cpp` wraps the checkout in a small RAII `ConnectionGuard` class whose destructor calls `pool_->return_connection(conn_)` — so the connection is always returned, even if an exception is thrown mid-query.
**TL;DR:** Mutex + condition_variable bounded pool with blocking checkout, self-healing dead-connection detection, and RAII-guaranteed return-on-exit via `ConnectionGuard`.

### Q6: Why C++ for this one microservice when the rest of the platform (API Gateway, Clearing) is Java?
**Polished answer:** The `main.cpp` log line literally says "Starting Authorization Service (High Throughput 10k RPS)". Authorization sits directly in the hot path of every single payment — it's the very first thing that runs after `payment_initiated` — so its latency and per-message resource cost multiply across 100% of traffic. C++ gives predictable low-latency execution with no GC pauses, tight control over thread/connection pooling, and lower per-connection memory overhead, which matters when you're running 100 worker threads and up to 100 DB connections per pod. Services further down the pipeline (Clearing, the API Gateway) are less latency-critical per hop or benefit more from Spring Boot's productivity, so the team made a deliberate polyglot choice: C++ where raw throughput/latency dominates, Java where developer velocity and ecosystem (Spring, JDBC, Kafka client maturity) dominate.
**TL;DR:** Authorization is the highest-volume, most latency-sensitive hop in the pipeline, so it gets the lowest-overhead language; other services optimize for developer productivity instead.

### Q7: How do you handle processing failures? What's the `.DLT` topic for?
**Polished answer:** The lambda passed to `enqueue_detach` wraps the entire parse-validate-publish sequence in a `try/catch`. If parsing the JSON throws, or the DB call throws an unhandled exception, the `catch` block republishes the *original, unmodified* payload to `payment_initiated.DLT` (dead-letter topic) instead of dropping it. This is important because a transient failure (bad JSON from an upstream bug, a DB blip that somehow escapes `AuthorizationEngine`'s own catch blocks) shouldn't silently vanish a payment message — it needs to be inspectable/replayable later. Note this is a second, outer safety net: `AuthorizationEngine::authorize()` itself already catches `pqxx::sql_error` and generic exceptions internally and converts them into an `out_reason` + `false` return (which flows to `payment_failed`, a normal business outcome), so the `.DLT` path is really for *unexpected* failures like a malformed message that can't even be parsed.
**TL;DR:** Two-tier error handling — expected DB/validation failures become a normal `payment_failed` event; anything unexpected (bad JSON, uncaught exceptions) gets dead-lettered to `payment_initiated.DLT` for replay/investigation instead of being lost.

### Q8: There's a comment in your code about a floating-point precision bug in the amount comparison. Walk me through it.
**Polished answer:** The DB stores `amount` as `NUMERIC(12,2)` — an exact decimal type — and the event carries it as a C++ `double`. To compare "does the event amount match the intent amount," the code converts both sides to strings and does a string comparison rather than comparing doubles directly (comparing floating point for exact equality is itself dangerous). The original bug was that naive double-to-string conversion (`std::to_string(double)`) uses `%g`-style formatting, which can produce something like `"13644.959999"` for a value that should print as `"13644.96"` — a value one cent off after truncation, not rounding. The fix, visible in the code now, uses `std::ostringstream oss; oss << std::fixed << std::setprecision(2) << event.amount;` which correctly *rounds* to 2 decimal places instead of truncating garbage precision. In a payment system, an off-by-one-cent mismatch would incorrectly reject (or worse, incorrectly accept) a legitimate transaction, so this class of bug is a big deal.
**TL;DR:** `std::to_string(double)` truncates instead of rounding and can produce garbage trailing digits; the fix uses `std::fixed << std::setprecision(2)` to round correctly to cents before string-comparing against the DB's exact `NUMERIC` value.

### Q9: How does graceful shutdown work?
**Polished answer:** `main.cpp` registers `signal_handler` for `SIGINT` and `SIGTERM` on a `volatile bool running` flag. `KafkaConsumer::start()` loops `while (running) { consumer_->consume(1000); ... }`, so when a signal flips `running` to `false`, the loop exits after at most one ~1-second poll cycle. On exit, `KafkaConsumer`'s destructor calls `consumer_->close()` (which lets the consumer group leave cleanly and commits final offsets), and `KafkaProducer`'s destructor calls `producer_->flush(10000)` to make sure any in-flight produced messages are actually sent before the process dies, rather than dropped. The handler also has a "press signal twice to force-exit" escape hatch (`std::exit(sig)` if `running` is already `false`).
**TL;DR:** SIGINT/SIGTERM flips a shared flag → poll loop exits within ~1s → consumer closes cleanly (commits offsets) → producer flushes pending messages before process exit.

### Q10: What Kafka delivery/ordering guarantees does this service actually provide — and where would you be honest that it *doesn't*?
**Polished answer:** This is an at-least-once pipeline, not exactly-once: `auto.offset.reset = "earliest"` and the default librdkafka consumer config means offsets are committed automatically as messages are polled/processed, without any transactional tie between "offset committed" and "downstream message produced." That means if the process crashes after authorizing a payment but before (or during) publishing to `payment_authorized`, on restart it will *not* replay that message (if the offset auto-committed) — a potential silent gap — or it *will* replay it (if it didn't), producing a duplicate authorization event downstream. Ordering is only guaranteed within a single partition; `PARTITION_UA` (unassigned) on the producer side means the broker's default partitioner (hash of key, or round-robin if no key) decides placement, and I don't see a key being set on `produce()`, so messages for the same transaction aren't guaranteed to land on the same partition or be processed in order relative to each other.
**TL;DR:** At-least-once delivery, no cross-service transactional guarantee between consuming and producing, and no explicit partition key — so duplicates are possible and cross-message ordering isn't guaranteed. This is honest "what would I improve" material for an interview.

## 11–25 — Deeper dives interviewers use to test real understanding

### Q11: Why is `running` a `volatile bool` instead of `std::atomic<bool>`? Is that actually correct C++?
**Polished answer:** `volatile` only tells the compiler "don't optimize away repeated reads of this variable" — it does *not* provide any memory-ordering or atomicity guarantee across threads on most real hardware/compilers. Technically, a signal handler modifying a plain `bool` (even `volatile`) that's read from another thread is undefined behavior under the strict C++ standard, though in practice it works on essentially every mainstream compiler/OS because a single-byte bool read/write is atomic at the hardware level on common platforms. The textbook-correct fix would be `std::atomic<bool> running` (or `sig_atomic_t` if strictly staying within signal-safety rules for what you can touch inside a handler) — I'd flag this as a known, low-risk technical debt item rather than pretend it's not there.
**TL;DR:** `volatile` isn't a real cross-thread synchronization primitive in C++; it "works" here in practice, but `std::atomic<bool>` is the textbook-correct choice and I'd call this out as something I'd fix.

### Q12: What's the difference between `ThreadPool::enqueue` and `enqueue_detach`, and why does `main.cpp` use the detach version?
**Polished answer:** `enqueue` wraps the task in a `std::packaged_task`, returns a `std::future` you can later `.get()` to retrieve the result or propagate an exception, and is meant for "fire this and I need the answer back." `enqueue_detach` just pushes a plain `std::function<void()>` onto the queue and returns nothing — it's fire-and-forget. `main.cpp` uses `enqueue_detach` because the Kafka message handler doesn't need a return value back on the consumer thread; the worker thread itself is responsible for publishing the result to Kafka. Using `enqueue` here would mean either blocking the consumer thread on `.get()` (defeating the whole point of the pool) or storing a growing pile of un-awaited futures, which is wasted bookkeeping.
**TL;DR:** `enqueue` returns a `future` for when you need the result back on the calling thread; `enqueue_detach` is fire-and-forget, which is exactly what a "consume → process → publish independently" worker needs.

### Q13/14: The `ThreadPool`'s task queue (`std::queue<std::function<void()>>`) is unbounded. What happens under a burst of, say, 100k messages, and how would you add backpressure?
**Polished answer:** Right now, `enqueue_detach` will happily push onto the internal `std::queue` no matter how deep it already is — there's no size cap and no blocking on the producer (consumer thread) side. Under a sudden burst, the consumer loop will keep pulling from Kafka and queuing work far faster than 100 worker threads can drain it, so the queue grows unbounded in memory, and (because it holds a copy of the string payload plus captured `shared_ptr`s) that's real heap growth that could eventually OOM the pod — especially under the 1Gi memory *limit* set in the k8s manifest. I'd fix this by adding a bounded queue with a max size, and making `enqueue_detach` block (or apply backpressure by pausing `consumer_->consume()` calls) once the queue is full — effectively coupling Kafka consumption rate to processing throughput, the same idea Kafka's own `max.poll.records`/manual pause-resume APIs are meant to solve.
**TL;DR:** Unbounded queue currently means a traffic spike can outrun 100 worker threads and grow memory without limit; the fix is a bounded queue plus pausing consumption (or blocking enqueue) once it's full, so backpressure flows back to the Kafka client.

### Q15: Explain the RAII pattern in `ConnectionGuard`. Why does this matter more in C++ than it would in Java?
**Polished answer:** `ConnectionGuard` is a tiny stack-allocated object whose constructor takes ownership of a checked-out connection, and whose destructor calls `pool_->return_connection(conn_)`. Because C++ guarantees destructors run when an object goes out of scope — including when an exception unwinds the stack — wrapping the checkout in this guard means the connection *always* gets returned to the pool, whether `authorize()` returns normally or throws partway through a query. In Java, you'd reach for `try-with-resources` (`AutoCloseable`) to get the same deterministic cleanup guarantee, because Java's garbage collector doesn't give you a deterministic "this connection is released right now" moment — without RAII or try-with-resources, connections could leak until GC (or never, if something holds a reference) instead of being returned to the pool immediately.
**TL;DR:** RAII (`ConnectionGuard`'s destructor) guarantees the DB connection is returned to the pool even on exceptions — C++'s equivalent of Java's try-with-resources, and necessary because C++ has no GC to eventually clean things up for you.

### Q16: Why does `from_json` accept both `transaction_id` and `transactionId` style keys?
**Polished answer:** `p.transaction_id = j.value("transaction_id", j.value("transactionId", ""))` — it tries snake_case first, falls back to camelCase. That's a defensive compatibility shim for a polyglot system: the upstream producer of `payment_initiated` (likely the Java API Gateway, Spring Boot conventions often lean camelCase in JSON DTOs) and this C++ consumer's own natural convention (snake_case, matching the Postgres column names) might disagree on casing, and rather than forcing a hard contract negotiation across teams/services, the parser just accepts either. Notably, this service's own `to_json` for outgoing events (`PaymentAuthorizedEvent`) emits camelCase (`transactionId`, `paymentIntentId`), so it's normalizing *inbound* payloads while being consistent with the rest of the system on the *outbound* side.
**TL;DR:** Defensive parsing for a polyglot pipeline where Java (camelCase) and C++/DB (snake_case) conventions can drift — accept either on input, standardize on camelCase for output to match the rest of the system.

### Q17: Why `pqxx::nontransaction` instead of a full transactional block for a read-only check?
**Polished answer:** `pqxx::nontransaction` is libpqxx's construct for read-only work where you explicitly don't need ACID transaction semantics (no rollback capability, no need to hold locks across statements) — it avoids the overhead of `BEGIN`/`COMMIT` for a query that's just reading current state to make a yes/no decision. Since `authorize()` never writes anything (all the actual state mutation — creating the `transactions` row, ledger entries — happens later, in the Persistence Worker after settlement), there's nothing here that needs transactional atomicity; using `nontransaction` is a reasonable, deliberate choice, not an oversight, as long as you're comfortable that a snapshot inconsistency between the LEFT JOIN's sub-parts (e.g., balance changing between the time you read it and the time downstream services act on this decision) is an accepted risk, not eliminated by this table.
**TL;DR:** `nontransaction` skips transaction-management overhead for a pure read — appropriate because this service never writes to the DB, but it does mean the balance you read is a point-in-time snapshot, not something locked/guaranteed to still be true by the time settlement happens.

### Q18: Why does the expiry check query Postgres for `CURRENT_DATE` instead of using the C++ server's local clock?
**Polished answer:** `authorize()` runs `SELECT EXTRACT(YEAR FROM CURRENT_DATE)::int AS yr, EXTRACT(MONTH FROM CURRENT_DATE)::int AS mo` instead of calling `std::chrono::system_clock::now()` locally. In a distributed system with multiple pods potentially running on hosts with slightly different clock skew (NTP drift, container clock issues), using the database's own clock as the single source of truth for "what date is it" for a business rule like card expiry means every replica of this service — no matter which node it's scheduled on — agrees on the same answer, instead of potentially disagreeing by a few seconds/minutes near a month/year boundary. It's a small extra round trip in exchange for eliminating an entire class of "which server's clock do we trust" bugs.
**TL;DR:** Using the DB's `CURRENT_DATE` as the canonical clock avoids clock-skew disagreements between replicas of this service running on different nodes — consistency over micro-optimizing away one query.

### Q19: Walk me through the multi-stage Dockerfile. Why two `FROM` stages?
**Polished answer:** The `builder` stage installs the full build toolchain (`build-essential`, `cmake`, `-dev` packages for librdkafka/libpqxx/nlohmann-json, `pkg-config`) and compiles the binary. The `runtime` stage starts fresh from `ubuntu:22.04` and only installs the *runtime* shared libraries (`librdkafka1`, `librdkafka++1`, `libpq5`, plus `ca-certificates`), then does `COPY --from=builder /app/build/authorization_service /app/authorization_service` to pull in just the compiled binary. This means the final image doesn't carry compilers, headers, or `-dev` packages — smaller image size, smaller attack surface, faster pulls in Kubernetes. The Dockerfile's own comment flags one intentional imperfection: it keeps `libpqxx-dev` (not just the runtime `.so`) in the final stage to be safe about exact `.so` version naming, acknowledging that in a stricter production setup you'd pin the specific runtime package instead.
**TL;DR:** Build stage has the full toolchain and compiles the binary; runtime stage only has the shared libraries needed to run it — smaller, more secure final image, standard multi-stage Docker pattern for compiled languages.

### Q20: Explain the `topologySpreadConstraints` in your Kubernetes deployment. Why does that matter for an authorization service specifically?
**Polished answer:** The manifest sets `maxSkew: 1`, `topologyKey: kubernetes.io/hostname`, `whenUnsatisfiable: ScheduleAnyway` — this tells the scheduler to try to spread the 2 replicas across different nodes (so the count of pods per node differs by at most 1) rather than letting the scheduler stack both replicas on the same node. If both replicas landed on one node and that node failed or got drained, authorization — which is on the critical path of *every* payment — would go fully down until Kubernetes rescheduled it, meaning a total payment outage instead of a partial-capacity degradation. `ScheduleAnyway` (as opposed to `DoNotSchedule`) means this is a soft preference, not a hard requirement — the pod will still schedule even if the constraint can't be perfectly satisfied, trading strict guarantees for scheduling flexibility.
**TL;DR:** Spreads the 2 replicas across different nodes so a single node failure doesn't take down 100% of authorization capacity — a soft (best-effort) high-availability constraint, appropriate for a payment-critical service with only 2 replicas.

### Q21: What is PgBouncer, and why does this service connect to `pgbouncer-service:5432` instead of Postgres directly?
**Polished answer:** PgBouncer is a lightweight connection pooler that sits in front of PostgreSQL. Every actual Postgres backend connection is relatively expensive in memory/process overhead on the Postgres side, and this one service alone is configured for up to 20–100 connections *per pod* (`DB_CONNS`), multiplied by however many replicas of authorization-service (and every other service) exist. Without a pooler, you could easily exhaust Postgres's `max_connections` across the whole platform. PgBouncer multiplexes many client-side connections (from this service's own `ConnectionPool`, which is itself already a pool!) down onto a much smaller number of real Postgres backend connections, so you effectively get "pooling of pools" — this app's pool controls concurrency on the app side, PgBouncer controls how many real DB backends that concurrency actually consumes.
**TL;DR:** PgBouncer multiplexes many application-side connections onto fewer real Postgres backend connections, preventing `max_connections` exhaustion when many replicas of many services each keep their own connection pool.

### Q22: You have `THREADS=100` but the k8s manifest sets `DB_CONNS=20`. Is that mismatch a problem?
**Polished answer:** Yes, it's a deliberate (or at least meaningful) tension worth being able to explain: with 100 worker threads but only 20 DB connections in the pool, at most 20 threads can be actively running a DB query at any instant — the other ~80 threads calling `authorize()` will block inside `ConnectionPool::get_connection()`'s `condition_.wait(...)` until a connection frees up. That's not necessarily wrong — it caps how much concurrent load hits Postgres (protecting the shared DB) at the cost of some worker threads sitting idle-but-blocked rather than doing useful work — but it does mean the "100 threads" number is partly aspirational/headroom for non-DB work (JSON parsing, publishing) rather than 100-way DB concurrency. I'd want to load-test this specific ratio rather than assume it's tuned correctly; if DB latency is the bottleneck, adding more threads past ~20-25 buys you very little.
**TL;DR:** With more threads (100) than DB connections (20), most threads will be blocked waiting for a connection rather than doing DB work — it protects Postgres from overload, but means the thread count is partly headroom, not a guarantee of 100-way DB concurrency; worth load-testing, not just assuming.

### Q23: Explain the k8s resource requests/limits (`128Mi/50m` request, `1Gi/2000m` limit). What happens if the service exceeds them?
**Polished answer:** The *request* (128Mi memory, 50m = 0.05 CPU cores) is what Kubernetes guarantees the pod and uses for scheduling decisions — it's the baseline the scheduler reserves on a node. The *limit* (1Gi memory, 2000m = 2 full CPU cores) is the hard ceiling: if the process tries to use more memory than 1Gi, the kernel's OOM killer terminates the container (which Kubernetes then restarts per its restart policy) — given the unbounded thread-pool queue issue from Q13/14, that's a very plausible failure mode under a traffic spike. If it tries to use more CPU than the limit, it isn't killed but gets CPU-throttled (cgroup throttling), which would show up as increased latency on every request rather than a crash — something you'd catch via container CPU-throttling metrics in Prometheus/Grafana, which the platform already has per the architecture doc.
**TL;DR:** Requests reserve guaranteed resources for scheduling; exceeding the memory *limit* gets you OOM-killed (a crash/restart), exceeding the CPU *limit* gets you throttled (silent latency increase) — both are real risks given the unbounded queue in Q13/14.

### Q24: Kafka gives you at-least-once delivery, meaning `payment_initiated` could be redelivered for the same transaction. How would you make this service idempotent against that?
**Polished answer:** Right now, re-processing the same `payment_initiated` message would just re-run the same read-only validation query and republish the same result — which is actually mostly harmless *for this specific service* since it's read-only and produces the same deterministic output given the same input state (modulo the balance changing between calls). The real risk is downstream: if `payment_authorized` gets published twice for the same `transaction_id`, whatever consumes it (Clearing Service) needs its own idempotency guard, likely via the `idempotency_keys` table already in the schema, or a `transaction_id` uniqueness check before acting. If I wanted this service itself to skip redundant work, I'd add a fast pre-check — e.g., a Redis `SETNX` or a DB lookup on `transaction_id` in `payment_events` — before doing the full authorization query, so a duplicate message short-circuits instead of re-running the whole validation and re-publishing.
**TL;DR:** This service's own logic is naturally close to idempotent (read-only, deterministic), but downstream consumers of `payment_authorized`/`payment_failed` need their own idempotency check (e.g., via `idempotency_keys` or a `transaction_id` dedupe) since Kafka only guarantees at-least-once delivery, not exactly-once.

### Q25: How would you unit-test `AuthorizationEngine` given it directly depends on a live Postgres connection?
**Polished answer:** The constructor takes a `std::shared_ptr<ConnectionPool>` as a dependency rather than constructing one internally, which is already good for testability — dependency injection means I can swap in a test double. For fast unit tests, I'd introduce an interface (abstract base class) that both `ConnectionPool` and a fake/mock pool implement, so `AuthorizationEngine` depends on the interface, not the concrete libpqxx-backed pool, letting me stub query responses without touching a real database. For integration-level tests that actually exercise the SQL (the LEFT JOIN logic, `NULL`-handling, expiry math), I'd spin up a real disposable Postgres via `testcontainers`-style Docker-based fixtures, seed known `users`/`payment_intents`/`payment_methods`/`accounts` rows, and assert on each rejection path individually (missing user, mismatched amount, expired card, insufficient balance) — since those are exactly the distinct `out_reason` branches in the code.
**TL;DR:** Constructor-injected `ConnectionPool` makes mocking feasible for unit tests; for the SQL logic itself, spin up a disposable real Postgres (testcontainers-style) and assert each rejection branch (missing user/intent/method, expired card, insufficient funds) independently.

## 26–50 — Systems design, trade-offs, and "what would you change" follow-ups

### Q26: Which Kafka delivery semantic — at-most-once, at-least-once, or exactly-once — does this service actually implement, and how do you know from the code?
**Polished answer:** At-least-once. There's no explicit manual offset-commit control visible (no `commitSync`/`commitAsync` calls, no `enable.auto.commit=false` config in `KafkaConsumer.cpp`), and no Kafka transactional producer/consumer setup (`transactional.id`, `initTransactions`, etc.) tying the consume-offset-commit to the produce-call atomically. That combination is the textbook signature of at-least-once: on a crash/restart, you might reprocess a message you'd already handled (auto-commit hadn't fired yet), but you'll never silently lose one. Exactly-once in Kafka specifically requires idempotent producers plus transactional read-process-write, which this code doesn't set up.
**TL;DR:** At-least-once — no transactional producer/consumer wiring visible, so duplicates are possible on crash-recovery, but messages are never silently dropped.

### Q27: Why is authorization a separate microservice instead of logic embedded in the API Gateway that receives the original payment request?
**Polished answer:** Separating it lets each service scale and fail independently: the API Gateway's job is to be a thin, fast front door (validate shape, idempotency-check via Redis, publish an event) — it shouldn't block a client-facing HTTP request on a potentially slower fraud/balance-check DB query. Publishing `payment_initiated` and returning "processing..." immediately (per the architecture doc's step-by-step flow) gives the client fast feedback while authorization happens asynchronously. It also means authorization logic — which is business-critical and likely to change independently (new fraud rules, new limit checks) — can be deployed, scaled, and even rewritten without redeploying or coupling to the gateway, and a slow/struggling Postgres only backs up this one service's queue instead of blocking every inbound HTTP request at the edge.
**TL;DR:** Keeps the client-facing API Gateway fast and decoupled from DB-dependent validation latency; lets authorization scale, fail, and evolve independently as its own bounded context.

### Q28: Walk through the full event chain (`payment_initiated` → `payment_authorized` → `payment_cleared` → `payment_settled`). Why pub/sub over direct service-to-service RPC calls?
**Polished answer:** Each stage (Auth → Clearing → Settlement → Persistence) consumes the previous stage's output topic and produces its own, forming a pipeline entirely mediated by Kafka rather than direct HTTP/gRPC calls between services. The big win is decoupling in time and failure domain: if Clearing Service is down or slow, `payment_authorized` events just sit safely in Kafka until it recovers — the API Gateway and Authorization Service keep running unaffected, instead of a synchronous call chain where one slow/down service blocks or fails the whole request chain. It also naturally gives you an audit trail/event log (reinforced by the separate `payment_events` table mirroring these events) and lets you add new consumers of any topic (e.g., a fraud-analytics service subscribing to `payment_authorized`) without touching the producer at all.
**TL;DR:** Event-driven pub/sub decouples each stage's uptime/latency from the others, gives natural buffering under load or partial outages, and lets you add new consumers without modifying upstream services.

### Q29: The authorization check reads the account balance, but the actual debit presumably happens later in Clearing/Settlement. Is there a race condition (time-of-check-to-time-of-use) risk?
**Polished answer:** Yes, structurally there is one: `authorize()` reads `a.balance` at time T and says "sufficient funds," but nothing in this service reserves or locks that balance — it's a plain `SELECT`, not a `SELECT ... FOR UPDATE` or a balance-hold/reservation write. If two payments for the same user are authorized concurrently (two different transaction_ids, both read the same starting balance before either is debited), both could pass the balance check even though only one can actually be honored once real debits happen downstream. This is a classic TOCTOU (time-of-check-to-time-of-use) gap. The realistic fix is either a reservation/hold pattern (write a pending debit row atomically as part of authorization, so a second concurrent authorization sees the reduced available balance) or having the ledger/settlement stage be the sole source of truth that can reject/roll back at the point of actual debit, with authorization treated as an optimistic pre-check rather than a guarantee.
**TL;DR:** Yes — the balance check is a plain read with no lock/reservation, so two concurrent authorizations for the same user could both pass against the same starting balance; the fix is a reservation/hold write at authorization time or treating this check as optimistic and letting settlement be the final arbiter.

### Q30: How do Kafka consumer groups work, and what happens if you run 2 replicas of authorization-service (as the k8s manifest does) against the same topic?
**Polished answer:** All instances of this service join the same consumer group id, `"authorization-service-group"`, hardcoded in `main.cpp`. Kafka guarantees that within one consumer group, each partition of `payment_initiated` is assigned to exactly one consumer instance at a time — so with 2 replicas, the broker splits the topic's partitions roughly in half between them (partition-level, not message-level load balancing). This gives you horizontal scaling (more replicas can consume more partitions in parallel, up to the partition count) and automatic failover (if one pod dies, its partitions get reassigned to the survivor during a rebalance) — but it also means your maximum useful parallelism at the consumer level is capped by the topic's partition count, independent of how many pods or threads you run.
**TL;DR:** Same group id means Kafka splits `payment_initiated`'s partitions across the 2 replicas — automatic load balancing and failover, but capped by however many partitions the topic has, not by pod/thread count.

### Q31: How would the partitioning strategy of `payment_initiated` affect per-transaction ordering guarantees?
**Polished answer:** Kafka only guarantees ordering *within* a single partition, not across the whole topic. If `payment_initiated` messages are keyed by (or hashed to a partition by) `transaction_id` or `user_id`, then all events for that same key are guaranteed to land in the same partition and be processed in the order they were produced — useful if a user could somehow have multiple related events that must be handled in sequence. If there's no key (round-robin/random partitioning), you get better load spreading across partitions but zero ordering guarantee between any two messages, even for the same user — which is fine here since each `payment_initiated` message is an independent transaction with no ordering dependency on another, but would matter a lot if you ever needed, say, "process this user's payments in the order they clicked pay."
**TL;DR:** Ordering is per-partition only; keying by `transaction_id`/`user_id` gives ordering guarantees for that entity at the cost of some load-balancing flexibility — currently not something this service's producer side (`payment_authorized`) sets, since it uses `PARTITION_UA`.

### Q32: What does `PARTITION_UA` mean in your `KafkaProducer::publish()` call, and what would change if you used a partition key instead?
**Polished answer:** `RdKafka::Topic::PARTITION_UA` stands for "unassigned" — it tells the broker/client "you choose the partition," which with librdkafka's default partitioner means round-robin (or a sticky variant) across the topic's partitions, since no message key is passed either (`NULL, 0` for the key argument in `produce()`). This maximizes even load-spreading across partitions/consumers downstream but gives up any ordering guarantee between messages for the same transaction or user. If I wanted, say, all events for one `transaction_id` to land on the same partition (useful if a downstream consumer needs to see a user's or transaction's events in order), I'd pass `event.transaction_id` (or `user_id`) as the key argument instead of `NULL` — the default partitioner hashes the key to deterministically pick a partition.
**TL;DR:** `PARTITION_UA` + no key = broker picks partition via round-robin, maximizing spread but giving up ordering; passing `transaction_id` as the key would pin all of a transaction's events to one partition for ordering, at some cost to even load distribution.

### Q33: Walk through the `std::packaged_task`/`std::future` mechanism in `ThreadPool::enqueue`. What C++17 feature (`std::invoke_result_t`) is doing the type deduction?
**Polished answer:** `enqueue` wraps the callable `f` and its args in a `std::packaged_task<return_type()>`, which pairs a callable with a promise that gets fulfilled automatically when the task runs. It wraps that in a `shared_ptr` (since `std::function`, used for the queue's element type, requires copyable targets, but `packaged_task` itself is move-only) so the lambda pushed onto the actual `std::queue<std::function<void()>>` just captures the `shared_ptr` and calls `(*task)()`. The caller immediately gets back `task->get_future()` — a `std::future<return_type>` — which they can later call `.get()` on to block until the result is ready (or to propagate an exception thrown inside the task). `std::invoke_result_t<F, Args...>` is a C++17 type trait that computes "what type does calling `F` with these `Args` return" at compile time, which is what lets `enqueue`'s return type (`std::future<...>`) be generic over any callable signature without the caller specifying it manually.
**TL;DR:** `packaged_task` + `future` gives a standard producer/consumer result-passing mechanism; `std::invoke_result_t` (C++17) is compile-time return-type deduction that makes `enqueue` generic over arbitrary callable signatures; wrapping in `shared_ptr` works around `packaged_task` being move-only while `std::function` needs copyable targets.

### Q34: The consumer loop polls with a 1000ms timeout. How does that affect shutdown latency after SIGTERM?
**Polished answer:** `consumer_->consume(1000)` blocks for up to 1 second waiting for a message before returning (with `ERR__TIMED_OUT` if nothing arrived). The `while (running)` check only happens *between* calls to `consume()`, so in the worst case — a signal arrives right after a `consume()` call has just started — the loop won't notice `running` flipped to false until that call returns, up to ~1 second later. In a Kubernetes context, that matters directly against the pod's `terminationGracePeriodSeconds`: if that grace period is shorter than roughly 1 second plus in-flight worker-thread completion time plus `producer_->flush(10000)` (which can itself take up to 10 seconds!), Kubernetes will SIGKILL the process before it finishes flushing pending produced messages, risking message loss on rolling deploys. I'd want to make sure the pod's grace period comfortably exceeds the sum of poll-timeout + max thread-pool drain time + producer flush timeout.
**TL;DR:** Up to ~1s delay to notice shutdown (bounded by the poll timeout) plus up to 10s for the producer flush on exit — the k8s `terminationGracePeriodSeconds` needs to comfortably exceed that sum, or rolling deploys risk killing the pod mid-flush and losing in-flight produced messages.

### Q35: Postgres stores `amount` as `NUMERIC(15,2)`/`NUMERIC(12,2)` (exact decimal), but your C++ struct uses `double amount`. Is that a latent bug risk, and how would you fix it?
**Polished answer:** Yes — `double` is a binary floating-point type that can't represent most decimal fractions (like 0.10) exactly, which is exactly the class of bug Q8's precision fix was working around at the comparison step. The current code mitigates the *symptom* (formatting the double to a rounded 2-decimal string before comparing) but the underlying representation is still lossy the moment JSON parsing does `j.at("amount").get<double>()`. A more robust fix would be to never carry money as a floating-point type at all: either parse/carry the amount as a fixed-point integer of cents (`int64_t amount_cents`), or keep it as a string end-to-end and only convert to a decimal type at the point of arithmetic (with a proper decimal/bignum library), matching what the DB's `NUMERIC` column is already doing. This is a common real-world payments bug class (see: numerous public "floating point in financial software" postmortems), so calling it out unprompted is a strong signal in an interview.
**TL;DR:** `double` for money is inherently risky (binary float can't represent most decimals exactly); the current code patches around it at the comparison step, but the more correct long-term fix is integer cents or a decimal type end-to-end, matching the DB's exact `NUMERIC` column.

### Q36: The architecture doc mentions Prometheus + Grafana for monitoring. This service doesn't appear to expose any metrics. How would you add observability to it?
**Polished answer:** Right now the service only has `std::cerr`/`std::cout` logging, no metrics endpoint. I'd add a small embedded HTTP endpoint (or push to a Prometheus Pushgateway, since this is a long-running consumer, not a request/response service, so a pull-based `/metrics` scrape endpoint on a lightweight embedded HTTP server would actually work fine here too) exposing counters/histograms for: messages consumed, authorization pass/fail counts (broken down by `out_reason` — expired card, insufficient funds, etc., which is gold for understanding real-world rejection patterns), DB query latency histogram, thread-pool queue depth (directly addresses the Q13/14 backpressure risk — you'd *see* the queue growing before it OOMs), and DB connection-pool wait time (surfaces the Q22 thread/connection ratio tension as a real metric instead of a guess). **TL;DR:** Add a `/metrics` endpoint (Prometheus client library) exposing consume rate, per-rejection-reason authorization outcomes, DB latency, thread-pool queue depth, and connection-pool wait time — directly turning the Q13/14/22 risk areas into observable, alertable numbers instead of code-review guesses; switch stderr logs to structured JSON for the ELK/Loki stack.

### Q37: Compare a synchronous REST call for authorization vs. this async Kafka-event approach. What latency/availability trade-offs does each bring?
**Polished answer:** A synchronous call (API Gateway → HTTP/gRPC → Authorization Service → response) gives the client an immediate, definitive yes/no in one round trip, which is simpler to reason about — but it tightly couples the Gateway's availability and latency to Authorization Service's, and if Authorization is briefly overloaded or Postgres is slow, that latency/failure propagates straight back to the end user's request. The async Kafka approach (what this codebase does) decouples that: the Gateway responds fast ("processing...") regardless of downstream load, and Authorization processes at its own pace, buffered by Kafka — better availability and load-shedding characteristics, at the cost of the client not getting an immediate final answer (needing polling, websockets, or a push notification to learn the outcome) and a more complex mental model (eventual consistency, harder to debug a single request end-to-end without distributed tracing).
**TL;DR:** Sync REST = simpler, immediate answer, but tightly couples availability/latency across services; async Kafka = better decoupling/availability/load-buffering, at the cost of needing an out-of-band way to tell the client the final outcome and more operational complexity to trace.

### Q38: Trace what happens architecturally if PostgreSQL becomes unavailable for a few seconds.
**Polished answer:** Worker threads calling `authorize()` hit the `pqxx` layer, which will throw when it can't connect or a query fails; `AuthorizationEngine`'s own `catch (const pqxx::sql_error&)` / `catch (const std::exception&)` blocks catch that, set `out_reason = "Database error during validation: ..."`, and return `false` — meaning every payment gets marked `FAILED` and routed to `payment_failed`, not silently dropped or retried, which from a correctness standpoint is safe (fail-closed) but from a business standpoint means real payments get rejected during a DB blip that a smarter design might have retried. Meanwhile, `ConnectionPool::get_connection()`'s reconnect-on-checkout logic (Q5) means once Postgres comes back, the very next thread to check out that slot gets a fresh working connection automatically, no manual intervention needed. A more resilient version would distinguish "DB is down" (retry-able, maybe requeue to `.DLT` or a delayed-retry topic) from "this specific payment is actually invalid" (a genuine business rejection), rather than collapsing both into the same `payment_failed` outcome.
**TL;DR:** Fails safe/closed — payments get marked `FAILED` (not stuck or dropped) during a DB outage, and connections self-heal once Postgres returns — but the current design can't distinguish "infrastructure blip, please retry" from "this payment is genuinely invalid," which I'd flag as a real gap.

### Q39: Why libpqxx instead of the raw C `libpq` library for Postgres access from C++?
**Polished answer:** `libpq` is Postgres's low-level C client library — you'd be manually managing connection handles, result sets, and string-based parameter binding with raw pointers and manual memory/error-code checking. `libpqxx` is the official C++ wrapper around it, giving you RAII-managed connections and result objects (so a `pqxx::connection` cleans itself up when it goes out of scope, results are proper C++ containers you can iterate/index), exceptions instead of error codes for failure handling (which is exactly what lets `AuthorizationEngine` use normal `try/catch` instead of checking a return code after every call), and a type-safe `exec_params` API for parameterized queries instead of manually building `PQexecParams` calls. It's the idiomatic choice for any modern C++ project talking to Postgres, the same way you'd reach for JDBC (not raw C bindings) from Java.
**TL;DR:** libpqxx is the RAII/exception-based idiomatic C++ wrapper around the raw C `libpq` API — safer resource management, type-safe parameterized queries, and normal C++ exception handling instead of manual error-code checking.

### Q40: Mechanically, how does a parameterized query (`exec_params`) differ from string-concatenated SQL at the wire-protocol level?
**Polished answer:** With string concatenation, the client builds one complete SQL string (values baked in) and sends it to Postgres, which parses and executes it as-is — if a value contains SQL-meaningful characters, they're interpreted as part of the query. With `exec_params`, libpqxx uses Postgres's extended query protocol: it sends the SQL text with placeholders (`$1`, `$2`, `$3`) in a `Parse` message, and sends the actual values *separately* in a `Bind` message, tagged with their data types — the server never re-parses the values as SQL text at all, it just substitutes them into the already-parsed query plan at execution time. That's why injection is structurally impossible this way — there's no step where user-controlled bytes are treated as SQL syntax — and as a side benefit, Postgres can cache/reuse the parsed query plan across calls with different parameter values (relevant if this were a prepared statement reused across many calls, though `exec_params` alone doesn't automatically name/cache a prepared statement unless you use `conn.prepare(...)` first).
**TL;DR:** Extended query protocol sends the SQL template and the parameter values as separate wire messages — values are never re-parsed as SQL text, which is structurally why injection can't happen, unlike plain string concatenation where the whole thing is parsed as one blob.

### Q41: The DB layer is one shared PostgreSQL cluster while the services around it are horizontally scaled. Where's the CAP-theorem-style consistency bottleneck in this design?
**Polished answer:** Every replica of every service (Authorization, Clearing, Settlement, the Gateway) ultimately reads/writes the same PostgreSQL cluster (via PgBouncer), so Postgres is the single consistency anchor — you get strong consistency for anything that actually round-trips through it, at the cost of it being the scaling bottleneck and single point of contention: enough concurrent load and every service's latency becomes bound by DB query latency, not their own compute (which is exactly the DB_CONNS/THREADS tension from Q22, multiplied across every service hitting the same cluster). The architecture doc mentions the `transactions` table is partitioned and sharded conceptually ("Sharding based on hash(transaction_id)") — that's the mitigation: partitioning spreads write/read load, but true horizontal write-scaling of Postgres (multi-primary sharding) is architecturally hard, so realistically this system favors consistency (C) and partition-tolerance is handled at the service layer (Kafka buffering) rather than the DB layer, with DB throughput as the ultimate ceiling on system-wide throughput.
**TL;DR:** Postgres (behind PgBouncer) is the single consistency anchor all services share, so it's also the system's real throughput ceiling; Kafka + service-level horizontal scaling buys you availability/partition-tolerance at the edges, but the DB is where the CAP trade-offs actually concentrate.

### Q42: If you had to scale this specific service to 10x throughput, what would you profile first, and how would you validate the hypothesis before changing anything?

I'd validate that by adding the metrics from Q36 first (DB query latency histogram, connection-pool wait time, thread-pool queue depth) under a realistic load test, rather than guessing — if connection-pool wait time dominates end-to-end latency, that confirms DB concurrency is the ceiling, and the fix is either more DB connections (with PgBouncer sized accordingly), query optimization (indexes on the join columns — I'd check `EXPLAIN ANALYZE` on that exact query), or read-replica routing for this read-only check. If instead CPU/JSON-parsing dominates, the fix is more threads/pods; if Kafka poll/produce latency dominates, it's partition count or broker-side tuning. **TL;DR:** Prior hypothesis (given the code's own thread/connection ratio) is DB round-trip latency is the ceiling — but I'd confirm with load-test metrics (connection-pool wait time, query latency, queue depth) before optimizing, rather than assuming, since the fix differs completely depending on which layer is actually the bottleneck.

### Q43: What's the difference between `ENTRYPOINT` and `CMD` in Docker, and why does this Dockerfile use `ENTRYPOINT ["/app/authorization_service"]`?
**Polished answer:** `CMD` sets a default command that's easily overridden by anything passed after the image name at `docker run` time; `ENTRYPOINT` sets the command that *always* runs, with any `docker run` arguments appended to it rather than replacing it. Using the exec-form array (`["/app/authorization_service"]`, not the shell-form string) means the binary runs as PID 1 directly, without an intermediate `/bin/sh -c` wrapper process — which matters for signal handling: `SIGTERM` sent by Kubernetes during a pod termination goes straight to the actual process (letting `signal_handler` in `main.cpp` catch it as designed), instead of being caught by a shell wrapper that might not forward it properly to the child process.
**TL;DR:** Exec-form `ENTRYPOINT` runs the binary directly as PID 1 (no shell wrapper), which is what lets Kubernetes's `SIGTERM` reach `main.cpp`'s signal handler cleanly for graceful shutdown — shell-form `CMD`/`ENTRYPOINT` risks a shell process swallowing or mishandling that signal.

### Q44: Why query the DB for `CURRENT_DATE` for the expiry check instead of calling `std::chrono::system_clock::now()` locally, revisited — what's the actual cost/benefit trade-off if you *did* use the local clock?
**Polished answer:** Using the local clock would save one extra `SELECT` per card-type authorization (a small latency win, and one fewer thing competing for a pooled DB connection under load), and for the vast majority of real-world cases the two approaches would agree since NTP-synced containers rarely drift by more than milliseconds. The cost is correctness risk concentrated right at month/year boundaries under clock skew — a genuinely rare but nasty class of bug (a card that should still be valid gets rejected, or vice versa, only on specific replicas, only near midnight on the last day of a month) that's hard to reproduce and debug precisely because it's non-deterministic across replicas. Given this is a payment-correctness-critical path, I think the current choice (DB-side clock) is the right trade of a small latency cost for eliminating an entire class of intermittent, hard-to-reproduce bugs — but I'd want to confirm that extra query isn't itself becoming a measurable latency contributor under the Q42 load-testing exercise.
**TL;DR:** Local clock is marginally faster but risks rare, non-deterministic, hard-to-debug expiry mismatches near month/year boundaries under clock skew between replicas; DB-side clock is slightly slower but removes that whole bug class — the right call for a payment-correctness path, worth revisiting only if profiling shows it's a real latency contributor.

### Q45: How does `std::shared_ptr<pqxx::connection>` prevent double-free or dangling-connection bugs as connections move between the pool and multiple worker threads?
**Polished answer:** `shared_ptr` keeps an atomic reference count; the underlying `pqxx::connection` object is only actually destroyed when the last `shared_ptr` pointing to it is destroyed or reset. In this design, the pool's internal `vector<shared_ptr<...>>` holds one reference, and each `ConnectionGuard` on a worker thread's stack holds another (temporarily) while it's checked out — so even in the moment a connection is "in flight" between being popped from the pool and being wrapped in a `ConnectionGuard`, there's always at least one live reference keeping it alive, and there's no path where two different owners could both believe they're responsible for deleting the same raw pointer (the classic C-style double-free bug). The reference counting itself is thread-safe (atomic increments/decrements), which is what makes it safe to pass these `shared_ptr`s across the mutex/condition_variable handoff between pool and worker threads without a data race on the connection's lifetime.
**TL;DR:** `shared_ptr`'s atomic reference counting means the connection object is only freed once every owner (pool's vector, any in-flight `ConnectionGuard`) releases it, eliminating double-free/dangling-pointer risk when connections are handed between the pool and multiple worker threads.

### Q46: The lambda in `main.cpp` captures `engine` and `producer` by value (as `shared_ptr`s) across many concurrently-running worker threads. Are `AuthorizationEngine` and `KafkaProducer` actually safe to share this way?
**Polished answer:** `AuthorizationEngine` itself holds no mutable state beyond the `shared_ptr<ConnectionPool>` — every call to `authorize()` checks out its *own* connection from the pool and only touches that connection, so concurrent calls from different threads don't share any mutable object underneath them; the `ConnectionPool`'s own internal state (the vector) is protected by its mutex. That part is genuinely thread-safe by construction. `KafkaProducer::publish()`, however, calls `producer_->produce(...)` and `producer_->poll(0)` directly on a single shared `RdKafka::Producer*` from multiple threads with no mutex around it in this codebase — librdkafka's own documentation states the `Producer` object's `produce()`/`poll()` methods are safe to call concurrently from multiple threads internally (it has its own internal locking), so this is *not* a bug, but it's exactly the kind of thing you should never assume without checking the library's own thread-safety contract — I'd want to be able to cite that guarantee explicitly rather than just "it seems fine in testing."
**TL;DR:** `AuthorizationEngine` is safe by construction (no shared mutable state, connection pool handles its own locking); `KafkaProducer`'s shared `RdKafka::Producer*` across threads is safe *because librdkafka's own API is documented as thread-safe for produce/poll* — not because the app code added locking — which is an important distinction to be able to articulate rather than assume.

### Q47: How would you add circuit breaking / retry-with-backoff if the authorization DB query starts timing out under sustained load?
**Polished answer:** Right now a slow/failing DB just makes every `authorize()` call slow or throw, cascading into every worker thread being tied up (queue backs up, per Q13/14) with no circuit breaker to stop sending traffic at a struggling DB. I'd add a simple state machine (closed/open/half-open) around the DB call: track a rolling error/timeout rate, and once it crosses a threshold, "trip" the circuit — for a window, skip the real query and fail fast (route straight to `payment_failed` with a clear "service degraded" reason, or better, to a delayed-retry topic) instead of piling more load onto an already-struggling Postgres and making recovery harder. After a cooldown, allow a small number of "half-open" probe requests through to check if the DB has recovered before fully closing the circuit again. This protects the DB from a pile-on effect (the classic "retry storm" that turns a brief blip into a full outage) and keeps worker threads from all being stuck waiting on the same slow dependency simultaneously.
**TL;DR:** Add a closed/open/half-open circuit breaker around the DB call: fail fast (route to `payment_failed`/delayed-retry) once error rate crosses a threshold instead of piling more concurrent queries onto an already-struggling Postgres, then probe for recovery before fully re-opening traffic.

### Q48: How would you write unit tests for `from_json`/`to_json` on `PaymentInitiatedEvent`, and what edge cases would you specifically target given how the code is written?

**TL;DR:** Target exactly the branches the code itself has special-cased: amount as string vs. number, snake_case vs. camelCase keys, missing-field defaults, and a malformed-amount-string throw path that should surface through the DLT mechanism — plus a round-trip serialization test to catch precision drift.

### Q49: This platform is polyglot — C++ for Authorization and Settlement, Java for the Gateway and Clearing. What are the real pros/cons of that choice for a team, beyond raw performance?
**Polished answer:** The upside beyond performance is "right tool for the job per bounded context" — the Gateway and Clearing benefit from Spring Boot's mature ecosystem (validation, DI, observability integrations, faster feature velocity for business-logic-heavy services), while Authorization and Settlement, sitting in the highest-throughput/lowest-latency part of the pipeline, benefit from C++'s control over memory and threading. The real cost is organizational, not technical: you now need engineers comfortable in both languages (or separate specialized teams, which risks silos and slower cross-service debugging when an issue spans a Java-to-C++ hop), duplicated tooling (two sets of CI/build pipelines, two dependency-management ecosystems, two sets of idioms for the "same" concerns like JSON parsing or DB pooling — you can literally see this in comparing this service's hand-rolled `ThreadPool`/`ConnectionPool` against what Spring Boot gives you almost for free), and a higher bar for a new hire to be productive across the whole system. I'd only justify polyglot for services where the performance difference is provably load-bearing (like this one claims, "10k RPS"), not as a default architectural style.
**TL;DR:** Polyglot buys you the best language per bounded context (Spring's productivity where business logic dominates, C++'s control where raw throughput dominates) at the real cost of duplicated tooling, hand-rolled infrastructure (this service's own ThreadPool/ConnectionPool vs. what Spring gives for free), and a higher bar for engineers to be productive system-wide — only worth it where the performance gap is provably load-bearing.

### Q50: If you redesigned this exact service in Java + Spring Boot instead of C++, what would change, and what would you gain or lose?
**Polished answer:** You'd lose the hand-rolled `ThreadPool` and `ConnectionPool` entirely — Spring Boot's `@KafkaListener` with a configured concurrency level replaces the manual consumer-loop + thread-pool dance, and HikariCP (Spring's default connection pool) replaces the custom mutex/condition_variable pool, both battle-tested and configuration-driven instead of maintained-by-hand C++. You'd gain faster development velocity, built-in metrics (Micrometer → Prometheus is nearly free in Spring Boot, directly solving Q36), and a much larger hiring pool of engineers who can maintain it. You'd lose the predictable low-latency/low-memory-overhead profile C++ gives you — JVM warm-up time, GC pauses (even with modern low-pause collectors, they're not zero), and generally higher baseline memory footprint per pod, which matters at "10k RPS" scale multiplied across however many replicas. The amount-as-`double` risk (Q35) would actually be easier to avoid in Java, since `BigDecimal` is the idiomatic, well-supported choice for money there, whereas C++ requires either a third-party decimal library or careful fixed-point-integer discipline. Net: you'd trade raw throughput-per-core and predictable latency for developer velocity and operational maturity — the same trade-off that presumably justified choosing C++ for *this* service in the first place, just in reverse.
**TL;DR:** You'd swap hand-rolled ThreadPool/ConnectionPool for Spring's `@KafkaListener` + HikariCP, gain built-in metrics and dev velocity, and get easier money-handling via `BigDecimal` — but lose C++'s predictable low-latency/low-memory profile, which is presumably exactly why this particular high-volume, latency-critical service was written in C++ in the first place.
